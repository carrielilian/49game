# 代理游戏财务管理需求文档

> 文档用途：技术开发、接口联调、功能测试与业务验收  
> 文档状态：按当前可运行原型及原型批注整理  
> 基准日期：2026-07-27  
> 适用原型：代理游戏财务平台

## 1. 背景与问题

代理游戏财务业务需要统一维护厂商、游戏、合同、结算公式和渠道映射，并完成外部收入导入、内部收入与退款拉取、游戏账户汇总、付款申请、实际付款和结算函留档。

当前需求以可运行原型和原型批注为产品基准。本文件将分散在各页面中的字段、交互、计算、快照和异常规则整理为统一口径，供技术开发和测试验收使用。

## 2. 目标

1. 建立厂商、游戏、合同、结算公式和内部渠道之间的基础数据关系。
2. 支持外部收入导入，以及内部收入、内部退款的拉取和结算。
3. 按游戏汇总结算结果，支持预付分成抵扣和付款申请。
4. 付款申请成功时冻结关键业务数据，保证后续付款与结算函可追溯。
5. 支持付款结果、请款凭证、结算函及收入汇总统计。
6. 为技术开发提供明确的数据口径，为测试提供可执行的验收标准。

## 3. 用户与场景

| 用户角色 | 核心任务 |
|----------|----------|
| 财务人员 | 维护结算公式、导入或拉取收入数据、执行结算、申请付款、登记付款结果、维护凭证 |
| 游戏运营人员 | 维护厂商、游戏、合同、合作内容和内部渠道游戏ID |
| 财务负责人/管理人员 | 查看付款记录、结算函和收入汇总，核对业务结果 |
| 测试人员 | 按字段、流程、状态、计算和异常规则完成验收 |

## 6. 通用体验与内容要求

### 6.1 页面与查询

1. 当前业务类型可切换“游戏盒 / 快爆”，切换后仅展示该业务类型下的数据。
2. 列表查询条件采用多条件 AND 关系。
3. “游戏ID / 游戏名称”以 `ID / 名称`形式展示。
4. 金额展示使用币种符号和千分位，小数保留两位。
5. 人民币使用 `￥`，美金使用 `$`。
6. 未产生的数据统一显示“-”。
7. 时间精确到秒时使用 `YYYY-MM-DD HH:mm:ss`；月份使用 `YYYY-MM`。

### 6.2 表单反馈

1. 必填项使用必填标识。
2. 字段校验失败时，在字段下方显示红色错误文案。
3. 多字段未完善时，显示红色提示“请完善所有信息”。
4. 保存成功时关闭对应抽屉并显示绿色提示“提交成功”，批注明确要求不关闭的功能除外。
5. 取消或关闭不保存本次未提交修改。

### 6.3 金额输入

1. 合同金额、合同合作内容金额及已付款项金额不得小于0。
2. 金额最多保留小数点后两位。
3. 汇率必须为正数小数，最多保留小数点后四位。

## 7. 功能要求

## 7.1 厂商管理

### 7.1.1 厂商列表

| 列 | 规则 |
|----|------|
| 厂商编号 | 系统生成；游戏盒通常使用1000号段，快爆通常使用2000号段 |
| 厂商名称 | 展示签约公司名称 |
| 发票信息 | 展示发票类型，支持列筛选 |
| 操作 | 仅提供“编辑” |

列表不展示汇总行。

### 7.1.2 添加/编辑厂商

厂商信息字段：

| 字段 | 必填 | 规则 |
|------|------|------|
| 厂商编号 | 否 | 添加时显示“-”；编辑时只读 |
| 厂商名称 | 是 | 公司全称 |
| 联系人 | 否 | 文本 |
| 手机 | 否 | 文本 |
| 邮箱 | 否 | 文本 |
| 单位地址 | 否 | 文本 |
| 发票信息 | 是 | 专票6%、专票3%、专票1%、普通发票、其他 |

银行信息字段：

| 字段 | 必填 | 布局 |
|------|------|------|
| 开户名称 | 是 | 第一行 |
| 开户银行 | 是 | 第一行，下拉 |
| 开户银行所在地 | 是 | 第一行，下拉 |
| 支行名称 | 是 | 第二行 |
| 银行卡号 | 是 | 第二行 |
| 银行代码 | 否 | 第二行 |

业务规则：

1. 厂商共有七个必填项：厂商名称、发票信息和五项必填银行信息。
2. 编辑时不可修改厂商编号和所属业务类型。
3. 修改发票信息后，使用“跟随发票”的结算公式扣税点同步变化。
4. 发票信息为“其他”时，结算公式中的扣税点允许手工填写。

## 7.2 游戏管理

### 7.2.1 游戏列表

主要列：

- 游戏ID / 游戏名称
- 合同游戏名称
- 厂商ID
- 厂商名称
- 付款方
- 已付游戏代理金
- 已付预付分成款
- 已付委托开发费
- 运营状态
- 操作

操作顺序固定为：

1. 编辑
2. 合同管理
3. 已付款项
4. 操作记录

“付款方”位于“运营状态”左侧。列表最后一行显示“查询总计”，三个已付款金额按币种分别汇总。导出文件包含除“操作”外的列表字段，列顺序与页面一致，金额展示口径与页面一致。

### 7.2.2 添加游戏

| 字段 | 必填 | 规则 |
|------|------|------|
| 游戏名称 | 是 | 游戏正式中文名称 |
| 游戏英文名称 | 否 | 英文结算函使用 |
| 合同游戏名称 | 是 | 合同签约名称 |
| 归属厂商 | 是 | 支持按厂商ID或名称搜索 |
| 付款方 | 是 | 4399、纯游、游乐、游戏之家、香港4399、游家时代 |
| 游戏负责人 | 否 | 文本 |
| 版号 | 是 | 有 / 无 |
| 运营状态 | 是 | 未上线 / 已上线，默认未上线 |
| 备注 | 否 | 多行文本 |

### 7.2.3 编辑游戏

1. 游戏ID只读。
2. 归属厂商只读。
3. 付款方只读，不允许在编辑时修改。
4. 其他字段沿用添加游戏规则。

### 7.2.4 游戏名称重名校验

1. 添加和编辑保存时均校验游戏名称是否重复。
2. 比较前去除名称首尾空格。
3. 与全部已有游戏名称做精确匹配。
4. 编辑时排除当前游戏自身。
5. 重名时阻止保存，并在游戏名称输入框下方显示“游戏名称已存在”。

## 7.3 合同管理

| 字段 | 必填 | 规则 |
|------|------|------|
| 游戏ID / 游戏名称 | 否 | 只读 |
| 合同编号 | 是 | 文本 |
| 支付币种 | 是 | 人民币 / 美金；首次保存前可选，保存后锁定 |
| 合同金额 | 是 | 不小于0，两位小数 |
| 合作内容 | 是 | 游戏代理金、预付分成款、委托开发费；至少一项 |
| 游戏代理金 | 条件必填 | 勾选对应合作内容时显示 |
| 预付分成款 | 条件必填 | 勾选对应合作内容时显示 |
| 委托开发费 | 条件必填 | 勾选对应合作内容时显示 |
| 补充说明 | 否 | 多行文本 |
| 合作状态 | 是 | 合作中 / 合作终止；默认合作中 |

业务规则：

1. 三项合同约定金额使用合同支付币种。
2. 取消某项合作内容时，清空对应合同约定金额和对应已付款金额。
3. 保存合同变更后写入游戏操作记录。

## 7.4 已付款项

1. 入口位于游戏列表操作列“合同管理”之后。
2. 未维护合作内容时，不允许维护已付款项，并提示先维护合同信息。
3. 仅展示当前合同已勾选的合作内容。

| 字段 | 必填 | 规则 |
|------|------|------|
| 游戏ID / 游戏名称 | 否 | 只读 |
| 合同编号 | 否 | 只读 |
| 已付游戏代理金 | 条件必填 | 不小于0，两位小数 |
| 已付预付分成款 | 条件必填 | 不小于0，两位小数 |
| 已付委托开发费 | 条件必填 | 不小于0，两位小数 |

保存后同步更新游戏列表、查询总计、导出和操作记录。

## 7.5 结算配置管理

### 7.5.1 列表与入口

每个游戏展示内部渠道和外部渠道两条公式。操作顺序：

1. 结算公式
2. 内部渠道
3. 操作记录

### 7.5.2 结算公式

内部渠道和外部渠道分别维护：

| 字段 | 必填 | 规则 |
|------|------|------|
| 扣税点 | 自动/条件填写 | 默认跟随厂商发票；发票为“其他”时手工填写 |
| 渠道费 | 是 | 0–100整数 |
| 分成 | 是 | 0–100整数 |

发票与扣税点映射：

| 发票信息 | 扣税点 |
|----------|--------|
| 增值税专用发票（6%） | 0% |
| 增值税专用发票（3%） | 3.36% |
| 增值税专用发票（1%） | 5.6% |
| 普通发票 | 6.72% |
| 其他 | 手工填写 |

结算公式口径：

`结算结果 = 金额基数 × (1 - 扣税点 - 渠道费) × 分成`

保存成功后同步更新列表公式和操作记录。

## 7.6 内部渠道

| 业务类型 | 代理渠道及总类 | 发行渠道及总类 |
|----------|----------------|----------------|
| 游戏盒 | 总类“游戏盒”：游戏盒付费、游戏盒内购、49广告联盟 | 总类“快爆”：快爆付费、快爆内购、快爆小游戏广告 |
| 快爆 | 总类“快爆”：快爆付费、快爆内购、快爆小游戏广告 | 总类“游戏盒”：游戏盒付费、游戏盒内购、49广告联盟 |

规则：

1. 总类使用黑色加粗文本，展示在对应具体渠道上方。
2. 每行包含勾选框、具体渠道名称和渠道游戏ID。
3. 勾选渠道后，渠道游戏ID必填。
4. 一个渠道允许填写多个游戏ID，使用英文半角逗号“,”分隔；保存时去除各项首尾空格并过滤空段。
5. 保存时清理各ID首尾空格和空段。
6. 内部收入和退款按渠道总类汇总，不按具体渠道分别生成主列表记录。

## 7.7 外部收入结算

### 7.7.1 外部渠道

仅允许以下渠道：

`小米、荣耀、华为、爱九游、vivo、oppo、B站、TapTap、应用宝、ios`

### 7.7.2 数据导入

导入字段：

1. 收入时间
2. 渠道
3. 游戏ID
4. 游戏名称
5. 厂商名称
6. 待结算金额

重复校验：

1. 按“收入时间 + 渠道 + 游戏ID”判断主列表和本次文件内的重复数据。
2. 单个重复提示“{游戏ID}数据重复上传”。
3. 多个重复游戏ID使用“、”连接，例如“4001、4002数据重复上传”。
4. 存在重复时不进入成功预览。

导入预览：

1. 列表字段与导入字段一致。
2. 第一行显示“总计”，仅汇总待结算金额。
3. 点击“确认导入”后写入主列表。
4. 新记录的结算收入和结算时间显示“-”。

### 7.7.3 结算

1. 未结算记录可执行结算。
2. 结算使用游戏的外部渠道结算公式。
3. 结算成功后写入结算收入和结算时间。
4. 结算后的记录可进入游戏账户汇总。

按钮状态：

1. 每月首次进入时“数据拉取”可用，“结算”不可用。
2. 财务中心仍存在未结算数据时，提示“财务中心还未结算完成”。
3. 拉取成功提示“已从财务中心拉取待结算数据”。
4. 拉取成功后“数据拉取”置灰，“结算”可用。
5. 同月再次进入保持已拉取状态。

### 7.8.2 结算

1. 主列表渠道仅展示总类“游戏盒 / 快爆”。
2. 代理渠道数据以待结算金额作为公式基数。
3. 发行渠道拉取值为财务中心结算收入，按当前业务口径写入。
4. 结算成功后写入结算收入和结算时间。

## 7.9 内部退款结算

### 7.9.1 数据拉取

数据来源为【财务中心－结算管理－玩家退款记录】。

最终按“月 + 游戏ID + 渠道总类”汇总成一条主列表记录。

渠道结构和财务中心数据类型与内部收入一致，取值规则如下：

| 渠道类型 | 取值规则 |
|----------|----------|
| 代理渠道 | 退款金额 |
| 发行渠道 | 退款金额 × 发行平台结算公式 |

按钮状态与内部收入结算一致；财务中心未完成退款结算时提示“财务中心还未结算完成”。

### 7.9.2 主列表与结算

1. 原始金额列名称为“退款金额”。
2. 计算结果列名称为“结算退款”。
3. 结算公式中的变量名称显示为“退款金额”。
4. 渠道仅展示总类“游戏盒 / 快爆”。

### 7.11.2 标记付款

| 字段 | 必填 | 规则 |
|------|------|------|
| 游戏ID、游戏名称 | 否 | 只读 |

金额计算变量：

- `pending`：待付款金额
- `remaining`：申请时剩余未抵扣分成款
- `rate`：申请时填写并冻结的汇率
- `contractCurrency`：合同支付币种
- `paymentCurrency`：付款币种
- `net = max(pending - remaining, 0)`
- `usdNet = max(pending / rate - remaining, 0)`

初始金额：

| 情况 | 条件 | 实际付款金额（￥） | 实际付款美金（$） |
|------|------|-------------------|------------------|
| 1 | 预付分成款≤0 | pending | 付款币种为美金时为 pending/rate，否则为空 |
| 2 | 预付分成款>0且合同支付币种为人民币 | net | net/rate |
| 3 | 预付分成款>0且合同支付币种为美金 | usdNet×rate | usdNet |

用户可修改初始金额。点击“标记已付款”后保存实付、付款时间、收款信息和备注，并将状态改为“已付款”；结算函保持申请时快照不变。

## 7.12 结算函

### 7.12.1 基础规则

1. 结算函在申请付款成功时生成并冻结。
2. 付款状态变化及标记付款填写的实际金额不改变结算函。
3. 标题为“{厂商名称} 与 {分成付款公司对应公司全称} 合作分成结算确认函”。
4. 支持下载中文或英文PDF模拟文件。
5. 4399和纯游不支持英文下载，点击后提示“{分成付款公司}的分成付款公司不支持英文版结算函下载”。

### 7.12.2 英文游戏名称

1. 申请付款时冻结游戏英文名称。
2. 英文结算函优先使用冻结的游戏英文名称。
3. 申请时未填写英文名称时，回退使用同一申请快照中的中文游戏名称。
4. 申请成功后再修改游戏英文名称，不影响既有英文结算函。

### 7.12.3 明细与汇总

1. 收入明细按游戏和渠道分组，连续月份合并为一行。
2. 收入区包含合作产品名称、结算时间、游戏产品收入①、结算公式和结算金额。
3. 退款存在时展示退款区；无退款时整段隐藏。
4. `合计②`为收入结算金额合计。
5. `合计④`为结算退款合计。
6. `总计②-④ = 合计② - 合计④`。
7. 公式中的收入基数显示为①，退款基数显示为③。

### 7.12.4 预付抵扣

仅申请快照中剩余未抵扣分成款大于0时展示“结算/抵扣金额”和“剩余未抵扣预付分成款”。

支付币种为人民币：

- 当总计不小于剩余时，抵扣金额等于剩余，抵扣后剩余为0。
- 当总计小于剩余时，抵扣金额等于总计，抵扣后剩余等于剩余减总计。

支付币种为美金：

- 先按冻结汇率将总计折算为美金。
- 再按上述规则与美金口径的剩余未抵扣分成款比较。

### 7.12.5 实际付款金额

1. 始终展示。
2. 使用申请付款时按标记付款三种情况计算并冻结的金额。
3. 付款币种为人民币时使用`￥`，为美金时使用`$`。
4. 不使用标记付款后手工填写的实际付款金额。
5. 不展示“支付金额（大写）”。

## 8. 状态与数据联动

### 8.1 结算记录状态

| 状态 | 说明 |
|------|------|
| 未结算 | 已导入或拉取，尚未执行结算 |
| 已结算、未申请 | 已产生结算收入或结算退款，可进入游戏账户余额 |
| 已申请 | 已纳入某次付款申请，不再重复计入可申请余额 |

### 8.2 付款记录状态

| 状态 | 可执行操作 |
|------|------------|
| 未付款 | 标记付款、结算函、请款凭证 |
| 已付款 | 详细信息、结算函、请款凭证 |

### 8.3 关键联动

1. 新增游戏后，结算配置管理自动出现该游戏。
2. 厂商发票信息变化时，跟随发票的扣税点同步变化。
3. 合同合作内容取消后，对应合同金额和已付款金额清空。
4. 已付款项变化后，游戏列表、游戏收入预付数据和收入汇总同步变化。
5. 结算完成后，游戏收入累计收入或累计退款同步变化。
6. 申请付款成功后，结算记录改为已申请，账户余额清零，付款列表新增记录。
7. 标记付款后，付款状态、付款时间和收入汇总中的结算付款金额同步变化。
8. 申请付款和结算函均以申请时快照为准，避免源数据变化造成历史记录漂移。

## 9. 用户故事

1. 作为游戏运营人员，我希望维护厂商和游戏资料，以便财务结算能够关联正确主体。

## 11. 实现与测试关注点

1. 申请付款快照和结算函快照必须持久化，不可在查看时重新读取最新主数据覆盖。
2. 新增的游戏英文名称快照字段应兼容历史付款记录；历史记录无该字段时回退中文名称。
3. 金额计算过程中建议统一使用最小货币精度或统一舍入方法，页面最终保留两位小数。
4. 汇率保存和计算最多使用四位小数，禁止使用标记付款时的临时输入覆盖申请快照汇率。
5. 内部渠道归类、拉取、列表、筛选、导出和统计必须使用同一“渠道总类”映射。
6. 外部收入重复校验需要同时检查历史数据和同一批次数据。
7. 合同取消合作内容的清空操作需要同时覆盖约定金额、已付款金额及其下游展示。
8. 测试应覆盖人民币/美金、无预付/有预付、全额抵扣/部分抵扣、无退款/有退款、支持/不支持英文函等组合场景。

## 12. 关键假设与开放问题

### 12.1 已采用的假设

1. 游戏名称重名范围为全部业务类型下的全部游戏，不仅限当前列表。
2. 游戏名称重名比较去除首尾空格，但区分其他字符差异。
3. 游戏英文名称选填，不作为申请付款前置条件；为空时英文函回退中文名称。
4. 历史付款记录若不存在新快照字段，允许读取可用的兼容回退值。
5. 原型中的文件上传、PDF下载和财务中心取数为交互模拟，正式开发需接入对应服务。

### 12.2 开放问题

1. 正式环境的角色权限、数据权限和审批权限需另行定义。
2. 财务中心接口字段、错误码、重试与幂等协议需在接口设计阶段确认。
3. 外部报表的文件格式、工作表名称、字段类型和最大数据量需在导入接口设计阶段确认。
4. 英文结算函的正式模板、渠道英文名和付款方英文资料需由业务/法务最终确认。
5. 金额和汇率在服务端的精度、舍入模式及税务口径需由财务确认后固化。
